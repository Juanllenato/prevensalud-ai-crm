Stack Técnico

Tecnologías de vanguardia

Cada pieza fue elegida con un propósito concreto. Aquí está qué hace cada tecnología dentro del sistema.

🧠
IA & Modelos de Lenguaje
DeepSeek-V3 Modelo principal
LLM que alimenta el asistente de negocio y genera los reportes ejecutivos. Elegido por su relación rendimiento/costo y su excelente comprensión de datos en español. Se accede vía Together AI con la API compatible con OpenAI.
Claude Haiku (Anthropic) OCR fallback
Se usa como respaldo de visión cuando Google Vision retorna texto ambiguo en imágenes de facturas. Su capacidad multimodal permite interpretar el contenido visual y extraer montos, fechas y proveedores con más contexto.
Google Cloud Vision API OCR primario
Extrae texto de imágenes de facturas enviadas por WhatsApp. Maneja fotos tomadas con celular, recibos arrugados y distintas tipografías. El resultado pasa por regex para detectar montos, fechas y nombre del proveedor.
OpenAI-compatible layer Abstracción
El cliente HTTP usa el SDK de OpenAI apuntando a Together AI. Esto permite cambiar de modelo (DeepSeek, Llama, Mistral) con solo editar una variable de entorno, sin tocar código de la aplicación.
⚙️
Backend & API
FastAPI (Python 3.12) Framework API
Framework async de alto rendimiento para construir todos los endpoints REST del CRM. Su sistema de dependencias (Depends) permite inyectar autenticación, permisos por rol y sesión de BD de forma declarativa en cada ruta.
SQLAlchemy 2.0 async ORM
ORM completamente asíncrono para todas las consultas a PostgreSQL. Permite escribir queries tipadas en Python sin SQL manual, con soporte para transacciones, joins complejos y el filtro de tenant por sucursal en cada consulta.
Pydantic v2 Validación
Valida y serializa todos los datos de entrada y salida de la API. Cada endpoint tiene schemas Input/Output separados. Si un dato no cumple el tipo o las reglas (ej: monto mínimo, longitud de texto), la API rechaza la petición con un error claro antes de llegar a la BD.
Redis 7 + Celery Workers async
Redis actúa como broker de mensajes. Celery ejecuta tareas en segundo plano: procesamiento OCR de facturas, envío de reportes por WhatsApp, alertas de cobranza vencida y actualización de vistas materializadas del manifiesto.
Alembic Migraciones
Gestiona el versionado del esquema de la base de datos. Cada cambio estructural (nueva columna, índice, tabla) genera un archivo de migración con el SQL exacto a aplicar, trazable en git y reversible con un comando.
🗄️
Base de Datos & Persistencia
PostgreSQL 17 Base de datos
Motor relacional principal. Almacena ventas, clientes, pagos, comisiones, citas y egresos. Se eligió PostgreSQL por su soporte nativo de Row Level Security (RLS), que es la capa de aislamiento entre sucursales a nivel de base de datos.
Row Level Security (RLS) Aislamiento
Política de seguridad a nivel de fila en PostgreSQL. Aunque el código de aplicación ya filtra por sucursal_id, RLS actúa como última línea de defensa: ninguna query — ni por error ni por ataque — puede retornar datos de otra sucursal.
Supabase PostgreSQL managed
Servicio administrado que provee PostgreSQL en la nube con backups automáticos, panel de administración y connection pooling via PgBouncer. Elimina la gestión manual del servidor de base de datos en producción.
Redis 7 Cache & Cola
Doble función: broker de mensajes para Celery (colas de tareas async) y caché para sesiones y datos frecuentes. El manifiesto diario se cachea en Redis para responder en <50ms sin golpear la BD en cada carga.
🎨
Frontend & UX
Next.js 14 + React 18 Framework UI
App Router de Next.js estructura el CRM en módulos (ventas, clientes, contabilidad, agenda, asistente IA). React 18 con Server Components permite que las páginas que no necesitan interactividad carguen más rápido sin JS al cliente.
TailwindCSS + ShadCN UI Diseño
Tailwind permite escribir estilos directamente en el JSX sin archivos CSS separados. ShadCN aporta componentes accesibles listos (modales, toasts, selects) que se copian al proyecto y se personalizan sin depender de una librería externa.
TanStack Query Estado del servidor
Gestiona todas las llamadas a la API con caché automático, revalidación en background, estados de carga/error y optimistic updates. Evita volver a hacer fetch de datos que no cambiaron y mantiene la UI sincronizada sin Redux ni boilerplate.
Markdown Renderer custom Chat IA
El asistente IA responde con Markdown (tablas, listas, negritas). Se construyó un renderer propio en React sin librerías externas que parsea títulos ##, listas, tablas con alineación y bloques de código — controlando exactamente qué se renderiza.
🔗
Integraciones Externas
Twilio WhatsApp Business Mensajería
Canal bidireccional de WhatsApp. Recibe imágenes de facturas desde administradores para el flujo OCR, y envía reportes diarios y alertas de cobranza a los socios. El webhook de Twilio valida la firma HMAC para evitar peticiones falsas.
Google Calendar API v3 Agenda
Sincroniza las citas del CRM con Google Calendar. Cuando se agenda una reconsulta o consulta, el evento se crea automáticamente en el calendario de la sucursal con los datos del cliente y el profesional asignado.
AWS S3 + CloudFront Storage
S3 almacena las imágenes de facturas subidas por WhatsApp y los PDFs de reportes generados. CloudFront actúa como CDN para que los PDFs se descarguen rápido desde Perú sin latencia del servidor principal en Europa.
☁️
Infraestructura & DevOps
Docker Compose Contenedores
Orquesta los servicios en producción: API FastAPI, workers Celery, Redis y el proxy Nginx. Un solo archivo define toda la infraestructura; el despliegue se hace con un script deploy.sh que hace pull, rebuild y restart sin downtime.
Hetzner VPS Servidor
Servidor dedicado en Europa con IP fija. Se eligió Hetzner por su costo predecible y alto rendimiento para cargas de trabajo constantes. El servidor corre Docker con todos los servicios del CRM más Nginx como reverse proxy con SSL.
GitHub Actions CI/CD Despliegue
Pipeline que se ejecuta en cada push a main: corre linting con Ruff, type check con mypy, tests unitarios, y si todo pasa hace deploy automático al servidor vía SSH. Ningún código llega a producción sin pasar por este pipeline.
JWT RS256 + RBAC Seguridad
Los tokens de sesión se firman con clave privada RSA (RS256), no con un secreto simétrico. Esto permite verificar tokens sin exponer la clave de firma. El RBAC de 9 roles controla qué endpoints puede llamar cada usuario según su función en la empresa.
Terraform IaC Infraestructura como código
Define en código todos los recursos de AWS (S3 buckets, políticas IAM, CloudFront distributions). Cualquier cambio en infraestructura es revisable en git, reproducible en staging antes de aplicar en producción y reversible con un comando.
Ciberseguridad

Seguridad por arquitectura,
no por suerte

Un CRM de salud maneja datos médicos, financieros y personales. Cada capa del sistema fue diseñada para que una sola vulnerabilidad no comprometa todo.

Modelo de defensa en profundidad

El sistema tiene 7 capas de seguridad independientes. Para que un atacante acceda a datos sensibles tendría que romper todas en orden.

Capa 1
🔐 Secretos en Variables de Entorno
Infra · .env + Pydantic Settings
Ningún secreto existe en el código fuente. Las API keys de DeepSeek, Together AI, Google, Twilio y AWS se leen en tiempo de ejecución desde variables de entorno. Pydantic Settings valida que todas existan al arrancar — si falta una, el servidor no inicia.
# app/core/config.py class Settings(BaseSettings): ANTHROPIC_API_KEY: str # falla si no existe TWILIO_AUTH_TOKEN: str # falla si no existe DATABASE_URL: SecretStr # oculta en logs automáticamente model_config = SettingsConfigDict(env_file=".env")
Capa 2
🛂 CORS Restrictivo
FastAPI · Middleware
El servidor solo acepta peticiones HTTP de orígenes explícitamente whitelisteados. Un sitio malicioso o un script externo no puede llamar a la API aunque tenga el token, porque el navegador bloqueará la petición antes de que llegue al servidor.
app.add_middleware( CORSMiddleware, allow_origins=settings.ALLOWED_ORIGINS, # ["https://crm.prevensalud.pe"] allow_credentials=True, allow_methods=["GET","POST","PUT","DELETE"], allow_headers=["Authorization","Content-Type"], )
Capa 3
🎫 JWT RS256 — Firma Asimétrica
Backend · security.py
Los tokens de sesión se firman con una clave privada RSA (RS256). La clave privada vive solo en el servidor. Para verificar un token basta la clave pública. Si un atacante obtiene la clave pública, no puede crear tokens falsos — necesitaría la privada.
payload = { "sub": str(user.id), "rol": user.rol.value, "sucursal_id": str(user.sucursal_id), "exp": datetime.utcnow() + timedelta(minutes=480), } token = jwt.encode(payload, settings.JWT_PRIVATE_KEY, algorithm="RS256")
Capa 4
🔒 RBAC — Control de Acceso por Rol
FastAPI · Depends(require_roles)
Cada endpoint declara explícitamente qué roles pueden acceder. Si el usuario autenticado no tiene el rol necesario, la API retorna 403 Forbidden antes de ejecutar cualquier lógica. Un asesor no puede ver la cartera aunque tenga un token válido.
@router.get("/cartera") async def listar_cartera( _: None = Depends(require_roles(Rol.ADMIN, Rol.JUSTA, Rol.SOCIO)), # ↑ cualquier otro rol → HTTP 403 automático ):
Capa 5
🏛️ Row Level Security (RLS)
PostgreSQL · Política de BD
Aunque el código de aplicación ya filtra por sucursal_id, PostgreSQL tiene una política RLS que garantiza que ninguna query — sin importar cómo se construya — pueda retornar filas de otra sucursal. Es la última línea de defensa ante bugs en el ORM.
-- Política en PostgreSQL CREATE POLICY tenant_isolation ON ventas USING (sucursal_id = current_setting('app.current_sucursal_id')::uuid); -- Resultado: incluso SELECT * FROM ventas -- solo devuelve registros de la sucursal activa
Capa 6
🧹 Zero-PII al LLM
services/llm.py · Sanitización
Antes de enviar cualquier dato al modelo de lenguaje, se aplica un sanitizador que elimina todos los campos PII: DNI, teléfono, email, datos médicos. El LLM solo recibe métricas, montos y cantidades. Aunque Together AI registre el prompt, no hay datos personales en él.
PII_FIELDS = {"dni","telefono","email","datos_medicos"} def sanitize_for_llm(data: dict) -> dict: return {k: v for k, v in data.items() if k not in PII_FIELDS}
Capa 7
💉 Prompt Injection Defense
services/llm.py · Delimitadores XML
Los mensajes del usuario se encapsulan en delimitadores XML antes de entrar al prompt. Esto impide que un usuario escriba instrucciones que el modelo confunda como parte del system prompt (ataque de prompt injection).
system_prompt = f"""Eres el asistente de PrevenSalud. <datos_del_sistema>{datos_sanitizados}</datos_del_sistema>""" user_msg = f"<pregunta_usuario>{input_usuario}</pregunta_usuario>" # → el modelo sabe que lo de adentro son datos, no instrucciones
Controles adicionales
🔏

Cifrado de campos sensibles

DNI y datos_medicos se cifran en reposo con pgcrypto (AES-256) antes de guardarse en PostgreSQL. Aunque alguien acceda directamente a la BD, los datos están cifrados.

encrypt_field() / decrypt_field() en security.py Clave de cifrado separada del JWT secret Nunca aparecen en logs ni en respuestas no autorizadas
AES-256 pgcrypto
🧾

Logs con PII Masking

El logger JSON del sistema tiene masking automático. Cualquier campo que coincida con la lista PII_FIELDS se reemplaza por "***" antes de escribirse al log.

Sin teléfonos ni DNIs en archivos de log Solo se loguea el ID del objeto, nunca su contenido PII Configurado en core/logging.py con JSONFormatter
PII Masking
📬

Webhook Validation

El webhook de Twilio (WhatsApp) valida la firma HMAC-SHA1 de cada petición. Si la firma no coincide, el endpoint retorna 403 sin procesar nada. Previene que actores externos inyecten mensajes falsos.

Signature del header X-Twilio-Signature verificada TWILIO_WEBHOOK_SECRET en variables de entorno Mismo patrón aplicado a Google Calendar webhooks
HMAC-SHA1
🛑

No Silent Failures

Está explícitamente prohibido usar except: pass. Los errores fallan ruidosamente con contexto completo, lo que impide que un fallo silencioso oculte una vulnerabilidad activa.

Excepciones de dominio propias (VentaInvalidaError, etc.) Handler global en main.py convierte a HTTP 4xx/5xx Sentry DSN para alertas de errores en producción
Fail Loud
✅

Validación Total de Inputs

Todos los datos de entrada pasan por schemas Pydantic v2 antes de llegar al servicio o la base de datos. Límites de longitud, tipos estrictos, rangos numéricos. Un input malformado nunca llega al ORM.

max_length en todos los campos de texto libre Imágenes OCR validadas por MIME type + 10 MB máx Schemas Input/Output separados (nunca exponer campos internos)
Pydantic v2
🔄

Retry con Backoff Exponencial

Las integraciones externas (WhatsApp, OCR, Calendar) tienen máximo 3 reintentos con backoff exponencial. Si el servicio externo falla, el flujo principal no falla — registra el error y continúa (degradación elegante).

Nunca una falla de Twilio rompe el registro de egreso Todas las llamadas externas en app/integrations/ solamente Logs de cada intento con timestamp y motivo de falla
Resiliente
